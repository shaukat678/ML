# Pandas for ML — Part 7: Categorical Features & Encoding ⭐

Now we're going to tackle one of the most important parts of preparing real-world data:

> **How do we convert categorical information into something an ML model can understand?**

This is especially important because real datasets are rarely made of numbers only.

A dataset might contain:

```text
Age
Salary
City
Gender
Education
Job_Type
Car_Type
```

Some are numerical, some are categorical.

Let's build this from the ground up.

---

# 1. What Is Categorical Data?

A categorical feature contains **categories/groups rather than continuous numerical quantities**.

Example:

```text
City

Karachi
Lahore
Islamabad
Karachi
Lahore
```

These are categories.

Another example:

```text
Car_Type

SUV
Sedan
Hatchback
SUV
```

Another:

```text
Payment_Method

Cash
Card
Online
```

---

# 2. Two Major Types

Categorical data can be divided into:

```text
Categorical
    │
    ├── Nominal
    │
    └── Ordinal
```

This distinction is extremely important.

---

# 3. Nominal Data

Nominal categories have **no natural order**.

For example:

```text
City:

Karachi
Lahore
Islamabad
```

There is no meaningful:

```text
Karachi < Lahore < Islamabad
```

Similarly:

```text
Color:

Red
Blue
Green
```

There is no mathematical ranking.

So:

> **Nominal = names/categories without order.**

---

# 4. Ordinal Data

Ordinal categories **do have an order**.

For example:

```text
Education:

High School
Bachelor
Master
PhD
```

There is a natural progression:

```text
High School
      ↓
Bachelor
      ↓
Master
      ↓
PhD
```

Another example:

```text
Satisfaction:

Poor
Fair
Good
Very Good
Excellent
```

There is an order.

But there's an important subtlety:

> The difference between categories isn't necessarily numerically equal.

For example, the "distance" between:

```text
Poor → Fair
```

doesn't necessarily equal:

```text
Good → Very Good
```

That's why encoding decisions matter.

---

# 5. Why Can't ML Directly Use Strings?

Suppose your dataset contains:

```text
City
-----
Karachi
Lahore
Islamabad
```

An algorithm works with mathematical operations.

It can't meaningfully calculate:

```text
Karachi × 0.73
```

So we need to transform:

```text
categories
     ↓
numbers
```

This process is:

# Encoding

---

# 6. The First Temptation: Number the Categories

You might think:

```text
Karachi   → 1
Lahore    → 2
Islamabad → 3
```

Easy!

But we've created a problem.

The model might interpret:

```text
3 > 2 > 1
```

and potentially treat the categories as ordered.

But:

```text
Islamabad > Lahore > Karachi
```

doesn't mean anything.

This is the **fake-order problem**.

---

# 7. Label Encoding

Label encoding assigns an integer to each category.

Conceptually:

```text
Male   → 0
Female → 1
```

or:

```text
SUV       → 0
Sedan     → 1
Hatchback → 2
```

For some situations, this is perfectly reasonable.

But for nominal features, blindly doing this can introduce artificial relationships.

---

# 8. Where Label Encoding Makes More Sense

Suppose:

```text
Experience_Level

Beginner
Intermediate
Advanced
Expert
```

You can represent:

```text
Beginner     → 0
Intermediate → 1
Advanced     → 2
Expert       → 3
```

There is a meaningful order:

```text
0 < 1 < 2 < 3
```

So ordinal encoding is appropriate.

---

# 9. One-Hot Encoding

For nominal categories, one-hot encoding is often a safer choice.

Suppose:

```text
City

Karachi
Lahore
Islamabad
```

One-hot encoding creates:

```text
Karachi   Lahore   Islamabad
   1         0         0
   0         1         0
   0         0         1
```

Notice what happened.

Instead of:

```text
Karachi = 1
Lahore = 2
Islamabad = 3
```

we create separate features.

---

# 10. Why Is This Better?

Because now:

```text
Karachi
```

becomes:

```text
[1, 0, 0]
```

while:

```text
Lahore
```

becomes:

```text
[0, 1, 0]
```

There is no artificial:

```text
Karachi < Lahore
```

relationship.

They're simply different categories.

---

# 11. Pandas Can Do This

You can use:

```python
pd.get_dummies(df["City"])
```

For example:

```python
import pandas as pd

df = pd.DataFrame({
    "City": [
        "Karachi",
        "Lahore",
        "Islamabad",
        "Karachi"
    ]
})
```

Then:

```python
pd.get_dummies(df["City"])
```

produces something conceptually like:

```text
   Islamabad  Karachi  Lahore
0      0         1        0
1      0         0        1
2      1         0        0
3      0         1        0
```

---

# 12. Multiple Categorical Columns

Suppose:

```python
df
```

contains:

```text
Gender
City
Car_Type
```

You can do:

```python
pd.get_dummies(
    df,
    columns=["Gender", "City", "Car_Type"]
)
```

Pandas will create dummy columns for the categories.

This is convenient for exploration and simple preprocessing.

---

# 13. But in ML, Prefer `OneHotEncoder`

In production ML workflows, you'll often see:

```python
from sklearn.preprocessing import OneHotEncoder
```

Why?

Because Scikit-learn's encoder integrates naturally with:

```text
Pipeline
ColumnTransformer
train/test split
```

and handles the train/test preprocessing workflow more safely.

---

# 14. The Important `handle_unknown`

Here's a real-world problem.

Training data:

```text
City

Karachi
Lahore
Islamabad
```

Later, your model receives:

```text
City = Peshawar
```

What happens?

The model has never seen Peshawar.

That's an **unknown category**.

We can tell `OneHotEncoder` how to handle this:

```python
encoder = OneHotEncoder(
    handle_unknown="ignore"
)
```

This is extremely useful in real ML systems.

---

# 15. Why Unknown Categories Matter

Imagine your model was trained in January:

```text
Karachi
Lahore
Islamabad
```

Then in June:

```text
Peshawar
```

appears.

A robust ML pipeline shouldn't crash just because a new category appears.

Therefore:

```python
OneHotEncoder(handle_unknown="ignore")
```

is often a good practical choice.

---

# 16. The Dummy Variable Trap

Suppose:

```text
City

Karachi
Lahore
Islamabad
```

One-hot encoding gives:

```text
Karachi   Lahore   Islamabad
1         0        0
0         1        0
0         0        1
```

Mathematically, one column can be inferred from the others:

```text
Islamabad = 1 - Karachi - Lahore
```

For some models, particularly linear regression, this creates perfect multicollinearity.

One traditional solution is to drop one category:

```python
OneHotEncoder(drop="first")
```

Then:

```text
Karachi   Lahore
1         0
0         1
0         0
```

Here:

```text
Karachi = 0
Lahore = 0
```

can represent the reference category:

```text
Islamabad
```

But don't memorize "always drop the first category." Whether to drop categories depends on the model and goal; regularized linear models, for example, can often handle the full one-hot representation.

---

# 17. Now the Interesting One: Target Encoding

You previously asked about this, and your concern was exactly right.

Suppose:

```text
City        Salary
Karachi     80,000
Karachi     90,000
Lahore      60,000
Lahore      70,000
Islamabad   100,000
Islamabad   110,000
```

We could calculate average salary per city:

```text
Karachi     → 85,000
Lahore      → 65,000
Islamabad   → 105,000
```

Then encode:

```text
Karachi     → 85000
Lahore      → 65000
Islamabad   → 105000
```

This is:

# Target Encoding

The category is represented using information derived from the target.

---

# 18. Why Is Target Encoding Powerful?

Suppose you have:

```text
10,000 different cities
```

One-hot encoding could create:

```text
10,000 columns
```

That's huge.

Target encoding can represent the category using a single numerical feature:

```text
City → average target
```

So:

```text
10,000 categories
```

might become:

```text
1 column
```

That's why target encoding can be extremely useful for **high-cardinality categorical features**.

---

# 19. But Here Comes the Danger 🚨

Suppose:

```text
City → Target Average
```

and you calculate the average using the **entire dataset**.

Then:

```text
training data
+
test data
```

are used to calculate the encoding.

Now the test target values have influenced your feature.

That's:

# Data Leakage

You have allowed information about the answer to sneak into the input.

---

# 20. A Simple Example

Suppose your target is:

```text
House Price
```

and:

```text
City = Karachi
```

You calculate:

```text
Average Karachi house price
```

using every house in the dataset.

But your test set contains houses whose prices you're supposed to predict.

You've now used those test prices to construct the feature.

It's like asking:

> "What is the average answer?"

before giving the exam.

The model has indirectly seen the answer.

---

# 21. Correct Target Encoding

The basic idea is:

```text
                 DATA
                  │
                  ↓
            Train / Test Split
             /           \
            ↓             ↓
        TRAIN             TEST
          │                 │
          ↓                 │
 Calculate encoding         │
 from TRAIN only            │
          │                 │
          ↓                 ↓
 Transform TRAIN       Transform TEST
                       using training
                       information
```

Never calculate target statistics using the test target.

---

# 22. Even Training Data Has a Leakage Problem

Here's an even deeper issue.

Suppose you're encoding the training rows themselves.

For a particular training row:

```text
City = Karachi
Target = 5,000,000
```

If you calculate Karachi's average using that same row's target, the row's own answer contributes to its feature.

With small categories, this can make the encoded feature overly optimistic.

A better approach is often:

> **Out-of-fold target encoding**

We'll cover that when we get to advanced preprocessing.

---

# 23. Smoothing

Another problem with target encoding:

Suppose:

```text
City = TinyTown
```

has only:

```text
1 house
```

and its price is:

```text
100 million
```

Naively:

```text
TinyTown → 100 million
```

That is probably unreliable.

Compare:

```text
Karachi → average of 50,000 houses
```

versus:

```text
TinyTown → average of 1 house
```

Clearly, the second estimate is much less reliable.

Target encoding therefore often uses **smoothing**.

The category estimate is pulled toward the overall target mean when the category has few observations.

Conceptually:

```text
few observations
      ↓
trust category less
      ↓
move toward global mean
```

This is an important advanced concept.

---

# 24. High Cardinality

Let's define this clearly.

Suppose:

```text
Gender
```

has:

```text
2 categories
```

Low cardinality.

```text
City
```

might have:

```text
100 categories
```

Higher cardinality.

```text
Product_ID
```

might have:

```text
500,000 categories
```

Extremely high cardinality.

---

# 25. Why High Cardinality Is a Problem

One-hot encoding:

```text
Product_ID
```

with 500,000 unique products could potentially create:

```text
500,000 columns
```

That's usually undesirable.

This is where you might consider:

* target encoding
* frequency encoding
* hashing
* embeddings
* domain-specific grouping
* dropping identifiers

The right choice depends on what the categorical feature actually represents.

---

# 26. Frequency Encoding

Here's another useful technique.

Suppose:

```text
City

Karachi
Karachi
Karachi
Lahore
Lahore
Islamabad
```

Count occurrences:

```text
Karachi     → 3
Lahore      → 2
Islamabad   → 1
```

Or frequencies:

```text
Karachi     → 3/6
Lahore      → 2/6
Islamabad   → 1/6
```

Now:

```text
City
 ↓
Frequency
```

This is called:

# Frequency Encoding

Unlike target encoding, it doesn't directly use the target variable.

---

# 27. Pandas Makes Frequency Encoding Easy

```python
frequency = df["City"].value_counts()
```

Then:

```python
df["City_Frequency"] = (
    df["City"].map(frequency)
)
```

Or normalized:

```python
frequency = df["City"].value_counts(
    normalize=True
)

df["City_Frequency"] = (
    df["City"].map(frequency)
)
```

This is a nice example of Pandas being extremely useful for feature engineering.

---

# 28. Another Important Technique: Grouping Rare Categories

Suppose:

```text
City

Karachi      50,000
Lahore       40,000
Islamabad    20,000
SmallTown1       5
SmallTown2       3
SmallTown3       2
...
```

You may decide to group rare categories:

```text
Karachi
Lahore
Islamabad
Other
```

Why?

Because thousands of extremely rare categories can produce:

* sparse features
* unstable statistics
* poor generalization

Again, this is a modeling decision, not a universal rule.

---

# 29. A Real ML Example

Suppose we're predicting:

```text
Taxi Fare
```

Our dataset:

```text
Distance
Passengers
Traffic
Car_Type
City
Payment_Method
Fare
```

Categorical:

```text
Car_Type
City
Payment_Method
```

Numerical:

```text
Distance
Passengers
Traffic
```

Target:

```text
Fare
```

So:

```python
X = df.drop(columns=["Fare"])
y = df["Fare"]
```

Then:

```python
numeric_features = [
    "Distance",
    "Passengers",
    "Traffic"
]

categorical_features = [
    "Car_Type",
    "City",
    "Payment_Method"
]
```

---

# 30. Build the Preprocessor

```python
from sklearn.compose import ColumnTransformer
from sklearn.preprocessing import StandardScaler
from sklearn.preprocessing import OneHotEncoder

preprocessor = ColumnTransformer(
    transformers=[
        (
            "num",
            StandardScaler(),
            numeric_features
        ),
        (
            "cat",
            OneHotEncoder(handle_unknown="ignore"),
            categorical_features
        )
    ]
)
```

Now the pipeline knows:

```text
Distance      → scale
Passengers    → scale
Traffic       → scale

Car_Type      → one-hot
City          → one-hot
Payment       → one-hot
```

---

# 31. Why This Is Better Than Manually Editing the DataFrame

You could manually do:

```text
select columns
↓
scale them
↓
select categories
↓
encode them
↓
combine them
```

But this gets messy.

Especially when you have:

```text
training data
testing data
validation data
production data
```

A pipeline makes the process consistent.

# 33. The Most Important Encoding Decision Tree

When you see a categorical column, ask:

```text
             Categorical?
                  │
          ┌───────┴────────┐
          ↓                ↓
       Nominal           Ordinal
          │                │
          ↓                ↓
   Is cardinality       Natural order?
      manageable?          │
      /       \            ↓
    YES       NO       Ordinal Encoding
     │         │
     ↓         ↓
One-Hot    Consider:
           target/frequency/
           hashing/etc.
```

But there is another question:

> Is the category actually an identifier?

For example:

```text
Customer_ID
Product_ID
Transaction_ID
```

If almost every value is unique, encoding it may be useless or harmful.

---

# 34. Important Distinction: ID vs Feature

Suppose:

```text
Customer_ID

10001
10002
10003
10004
```

Don't assume:

```text
Customer_ID → useful feature
```

An ID is usually just an identifier.

But sometimes an identifier-like column can contain information—for example, a product code may encode meaningful hierarchy. You need to understand the domain before deciding.

---

# 35. One More Important Pandas Tool

```python
df["City"].nunique()
```

This tells you how many unique categories exist.

For example:

```text
3
```

Then:

```python
df["City"].value_counts()
```

might give:

```text

```

These two commands are extremely useful for understanding categorical features.

# 36. Your Categorical Data Checklist

When you encounter a categorical feature, ask:

### Question 1

What type?

```text
Nominal?
Ordinal?
Identifier?
```

### Question 2

How many categories?

```python
df["column"].nunique()
```

### Question 3

How frequently do they occur?

```python
df["column"].value_counts()
```

### Question 4

Are there rare categories?

```text
YES → perhaps group them
```

### Question 5

Is one-hot feasible?

```text
few categories → usually easy
thousands/millions → rethink
```

### Question 6

Could target encoding help?

```text
high-cardinality → potentially
```

### Question 7

Could target leakage occur?

```text
ALWAYS CHECK
```

---

# 37. The Golden Rule of Target Encoding 🔥

Burn this into your memory:

> **Never use target information from the validation/test data to create features.**

Incorrect:

```text
Entire dataset
      ↓
Calculate target mean by category
      ↓
Split data
```

Correct:

```text
Dataset
   ↓
Split
   ↓
Train ──→ calculate encoding
   │
   └────────→ transform train

Test ─────────→ transform using
                training encoding
```

And for robust training encodings, we'll later discuss **cross-fitting/out-of-fold encoding**.
