# Pandas for ML — Part 9: Feature Engineering 🚀

This is one of the **most important topics in practical ML**.

So far, we've mostly learned how to clean and transform existing data.

Now we ask a more powerful question:

> **Can we create better information from the information we already have?**

That's **Feature Engineering**.

---

# 1. First: What Is a Feature?

Suppose we're predicting taxi fare.

Our raw dataset is:

| Distance | Traffic | Passengers | Fare |
| -------: | ------: | ---------: | ---: |
|     5 km |       2 |          1 |  500 |
|    10 km |       7 |          2 | 1200 |
|     3 km |       8 |          1 |  600 |

Here:

```text
Distance
Traffic
Passengers
```

are **features**.

And:

```text
Fare
```

is the **target**.

---

# 2. What Is Feature Engineering?

Feature engineering means:

> **Creating, transforming, or selecting features so that useful patterns become easier for the ML model to learn.**

For example:

```text
Distance
Traffic
```

could become:

```text
Traffic per km
```

or:

```text
Distance × Traffic
```

or:

```text
Distance / Traffic
```

depending on the problem.

---

# 3. Think Like This 🧠

Imagine you're trying to predict whether a student will pass.

Raw data:

```text
Study Hours = 8
Sleep Hours = 4
Attendance = 60%
```

You could create:

```text
Study/Sleep Ratio
```

$$
\frac{StudyHours}{SleepHours}
=
\frac{8}{4}
=
2
$$

Or:

```text
Study Hours × Attendance
```

The raw columns contain information.

Feature engineering tries to expose **relationships** in that information.

---

# 4. Why Do We Need Feature Engineering?

Imagine a model sees:

```text
Distance = 10
Traffic = 8
```

Maybe the real-world effect isn't:

```text
Fare = a × Distance + b × Traffic
```

Instead, traffic matters more when the distance is long.

Then an interaction might help:

$$
Distance \times Traffic
$$

For:

```text
Distance = 10
Traffic = 8
```

we get:

$$
10 \times 8 = 80
$$

Now the model has a feature representing:

> **Long distance under heavy traffic.**

---

# 5. Feature Engineering Is Basically Giving the Model Better Clues

Think of an ML model as a detective.

Raw data:

```text
Distance = 20
Traffic = 9
```

You say:

> "Here are the facts."

Feature engineering says:

> "I've also calculated something that might reveal the relationship."

That's why good features can dramatically improve a model.

---

# 6. Mathematical Transformations

The simplest feature engineering technique is transforming an existing feature.

Suppose:

```text
Salary
```

has values:

```text
20,000
30,000
50,000
1,000,000
10,000,000
```

This distribution is heavily skewed.

We can create:

```text
Log_Salary
```

using:

```python
import numpy as np

df["Log_Salary"] = np.log1p(df["Salary"])
```

`log1p(x)` means:

$$
\log(1+x)
$$

and is safer when zeros are possible.

---

# 7. Why Log Transformation?

Look at:

```text
Salary = 10,000
Salary = 100,000
Salary = 10,000,000
```

The raw values differ enormously.

Log transformation compresses the scale.

Conceptually:

```text
Raw:

10,000
100,000
10,000,000

        ↓ log

~9.21
~11.51
~16.12
```

The extreme values become less dominant.

This can make some patterns easier for certain models to learn.

---

# 8. Important: Don't Log Everything

You shouldn't automatically do:

```python
np.log1p(df)
```

to every column.

Log transformation is particularly useful for variables that are:

* positive
* strongly right-skewed
* spanning several orders of magnitude

Examples can include:

```text
income
house price
population
sales
number of transactions
```

But it depends on the distribution and model.

---

# 9. Ratios

Ratios are extremely useful in feature engineering.

Suppose:

```text
Distance
Traffic
```

You might create:

```python
df["Traffic_per_km"] = (
    df["Traffic"] / df["Distance"]
)
```

Now:

$$
TrafficPerKm =
\frac{Traffic}{Distance}
$$

This represents something different from either feature individually.

---

# 10. Real-World Example: Student

Suppose:

```text
Study_Hours
Sleep_Hours
```

Create:

```python
df["Study_Sleep_Ratio"] = (
    df["Study_Hours"] /
    df["Sleep_Hours"]
)
```

If:

```text
Study = 8
Sleep = 4
```

then:

$$
Ratio = 2
$$

This could represent:

> How heavily the student's available time is tilted toward studying.

But remember: a feature being mathematically possible doesn't mean it's automatically useful. Validate it.

---

# 11. Division Has a Trap ⚠️

Suppose:

```text
Distance = 0
Traffic = 5
```

Then:

$$
\frac{Traffic}{Distance}
$$

becomes undefined.

So before creating ratios, think about zero denominators.

You might use:

```python
df["Traffic_per_km"] = (
    df["Traffic"] /
    df["Distance"].replace(0, np.nan)
)
```

Then decide how to handle the resulting missing values.

---

# 12. Interactions

Suppose:

```text
Distance
Traffic
```

You can create:

```python
df["Distance_Traffic"] = (
    df["Distance"] *
    df["Traffic"]
)
```

This is an **interaction feature**.

It tells the model:

> The effect of one variable may depend on another.

---

# 13. Another Example

Suppose we're predicting salary:

```text
Experience
Education_Level
```

Maybe:

```text
Experience = 10
Education = Master's
```

has a different effect than:

```text
Experience = 10
Education = Bachelor's
```

The relationship between them may matter.

This can be represented using interaction features, although categorical interactions are usually handled more carefully through encoding/model pipelines.

---

# 14. Polynomial Features

Suppose the relationship is curved rather than straight.

Maybe:

$$
y = x^2
$$

A linear model:

$$
y = ax+b
$$

cannot directly represent that curvature.

We can create:

```text
x²
```

using:

```python
df["x_squared"] = df["x"] ** 2
```

Now the model can use:

```text
x
x²
```

to represent nonlinear relationships.

---

# 15. Example

Suppose:

```text
Years_Experience
```

has:

```text
1
2
3
4
5
```

Create:

```python
df["Experience_Squared"] = (
    df["Years_Experience"] ** 2
)
```

Now:

| Experience | Experience² |
| ---------: | ----------: |
|          1 |           1 |
|          2 |           4 |
|          3 |           9 |
|          4 |          16 |
|          5 |          25 |

This gives a linear model access to a curved relationship.

---

# 16. Polynomial Features With Scikit-learn

You don't always have to manually create them.

```python
from sklearn.preprocessing import PolynomialFeatures

poly = PolynomialFeatures(
    degree=2,
    include_bias=False
)
```

For:

```text
x1
x2
```

degree 2 can generate features conceptually like:

```text
x1
x2
x1²
x1*x2
x2²
```

Notice:

> Polynomial features also create interactions.

This can increase the number of features very quickly, so use them thoughtfully.

# 17. Binning

Sometimes a continuous variable is easier to interpret in groups.

Suppose:

```text
Age
```

contains:

```text
18
22
31
45
67
```

We could create:

```text
Age_Group
```

such as:

```text
18–25
26–35
36–50
51+
```

This is called:

# Binning

---

# 18. Pandas `cut()`

For example:

```python
df["Age_Group"] = pd.cut(
    df["Age"],
    bins=[0, 18, 30, 50, 100],
    labels=[
        "Child",
        "Young",
        "Adult",
        "Senior"
    ]
)
```

Now a continuous feature becomes a categorical feature.

---

# 19. When Is Binning Useful?

Suppose a person's age effect isn't smooth.

Maybe:

```text
18–25 → high risk
26–40 → low risk
41–60 → medium risk
60+   → high risk
```

A raw linear relationship might not capture that well.

Bins can provide a simpler representation.

But:

> Don't bin automatically.

Binning also throws away information.

For example:

```text
Age 30
Age 31
```

might become the same category even though they aren't exactly equal.

# 20. Date & Time Features 🕒

Dates are incredibly useful.

Suppose your dataset contains:

```text
Order_Date
```

as:

```text
2026-08-28
```

A model can't directly make much use of the raw string.

We can extract:

```text
Year
Month
Day
Day_of_week
Hour
Weekend
Quarter
```

---

# 21. Convert to Datetime

Pandas:

```python
df["Order_Date"] = pd.to_datetime(
    df["Order_Date"]
)
```

Then:

```python
df["Year"] = df["Order_Date"].dt.year
df["Month"] = df["Order_Date"].dt.month
df["Day"] = df["Order_Date"].dt.day
df["DayOfWeek"] = df["Order_Date"].dt.dayofweek
```

Now one raw column has become several useful features.

---

# 22. Weekend Feature

This is a classic real-world feature.

```python
df["Is_Weekend"] = (
    df["Order_Date"].dt.dayofweek >= 5
)
```

Remember:

```text
Monday    → 0
Tuesday   → 1
...
Saturday  → 5
Sunday    → 6
```

So:

```text
dayofweek >= 5
```

means Saturday or Sunday.

---

# 23. Hour Features

Suppose we're predicting taxi demand.

Raw:

```text
Pickup_Time
```

Extract:

```python
df["Hour"] = df["Pickup_Time"].dt.hour
```

Now you can identify:

```text
00 → midnight
08 → morning rush
13 → afternoon
18 → evening rush
23 → late night
```

This is much more useful.

---

# 24. Peak Hour Feature

This connects directly to a feature you were interested in earlier.

Suppose:

```text
Peak hours:
7–9 AM
5–8 PM
```

You could create:

```python
df["Is_Peak"] = (
    df["Hour"].isin([7, 8, 9, 17, 18, 19, 20])
)
```

Now:

```text
Hour = 18
```

becomes:

```text
Is_Peak = True
```

This is domain-driven feature engineering.

# 25. Aggregation Features

Here's a very important real-world technique.

Suppose you have transactions:

| Customer | Amount |
| -------- | -----: |
| A        |    100 |
| A        |    200 |
| A        |    500 |
| B        |     50 |
| B        |    100 |

We can calculate:

```text
Customer_Total
Customer_Average
Customer_Transaction_Count
```

Using Pandas:

```python
df["Customer_Total"] = (
    df.groupby("Customer")["Amount"]
      .transform("sum")
)
```

And:

```python
df["Customer_Average"] = (
    df.groupby("Customer")["Amount"]
      .transform("mean")
)
```

And:

```python
df["Customer_Count"] = (
    df.groupby("Customer")["Amount"]
      .transform("count")
)
```

These can be extremely powerful features.

---

# 26. Why `transform()`?

This is worth understanding.

Suppose:

```text
Customer A
Customer A
Customer A
Customer B
Customer B
```

`groupby().agg()` normally produces one row per group.

But:

```python
groupby().transform()
```

returns the result aligned with the original rows.

So:

```text
Customer    Amount    Customer_Total
A           100       800
A           200       800
A           500       800
B            50       150
B           100       150
```

That's why `transform()` is so useful for feature engineering.

---

# 27. 🚨 Aggregation Leakage

There's an important danger here.

Suppose you're predicting:

```text
Future purchase amount
```

and you calculate:

```text
Customer_Total
```

using **future transactions**.

You've accidentally given the model information from the future.

That's data leakage.

Feature engineering must respect **time and information availability**.

Ask:

> "Would this information actually be known at prediction time?"

This is one of the most important questions in real ML.

---

# 28. Time-Series Leakage

Suppose we're predicting:

```text
Tomorrow's sales
```

You calculate:

```text
Monthly_Total
```

using the entire month.

But tomorrow's sales are included in that total.

That's cheating.

Instead, use only information available before the prediction moment.

For example:

```text
Past 7-day sales
```

could be legitimate.

---

# 29. Rolling Features

This leads to one of the most powerful Pandas techniques for time-series data.

Suppose:

```text
Date        Sales
Aug 1       100
Aug 2       120
Aug 3       150
Aug 4       130
```

We can calculate a rolling average:

```python
df["Rolling_3_Day"] = (
    df["Sales"]
      .rolling(3)
      .mean()
)
```

Conceptually:

```text
Day 1 → insufficient data
Day 2 → insufficient data
Day 3 → average of Days 1–3
Day 4 → average of Days 2–4
```

But if predicting the current day's value, you often need to **shift first** so the current target isn't included.

For example:

```python
df["Previous_3_Day_Avg"] = (
    df["Sales"]
      .shift(1)
      .rolling(3)
      .mean()
)
```

That means:

> Use the previous three observations, not the current one.

This distinction is critical.

# 31. Feature Engineering vs Feature Selection

Don't confuse these.

### Feature Engineering

Create new features.

```text
Distance
Traffic

        ↓

Distance × Traffic
Traffic / Distance
```

### Feature Selection

Choose which features to keep.

```text
100 features
     ↓
select useful 20
```

So:

```text
Engineering = create/transform
Selection = choose
```

We'll study feature selection separately.

# 34. `np.where()` — Very Useful

Suppose:

```text
Age >= 18
```

means adult.

You can create:

```python
df["Is_Adult"] = np.where(
    df["Age"] >= 18,
    1,
    0
)
```

So:

```text
Age    Is_Adult
15        0
20        1
17        0
30        1
```

This is a very common ML feature-engineering pattern.

# 35. Multiple Conditions

Suppose:

```text
Traffic > 7
AND
Hour is peak
```

You might create a feature such as:

```python
df["Heavy_Peak_Traffic"] = (
    (df["Traffic"] > 7) &
    (df["Is_Peak"])
).astype(int)
```

Now:

```text
Heavy_Peak_Traffic
```

is:

```text
1 → heavy traffic during peak time
0 → otherwise
```

This is a domain-informed feature.

# 36. ⚠️ The Most Important Question

Before creating any feature, ask:

> **Could I have known this value at the exact moment the prediction was made?**

If the answer is:

```text
NO
```

don't use it.

Example:

Predicting:

```text
Loan Default
```

Don't create:

```text
Total payments made after the loan default
```

because that's future information.

# 38. Feature Explosion

Suppose you have:

```text
100 features
```

and start creating:

```text
x1*x2
x1*x3
x1*x4
...
```

You could quickly end up with thousands of features.

More features ≠ automatically better model.

It can lead to:

* overfitting
* slower training
* more memory usage
* harder interpretation
* noisy features

So:

> Create features with a reason.

---

# 39. The Golden Feature Engineering Rules 🔥

Memorize these:

### Rule 1

> **Understand the domain before creating features.**

### Rule 2

> **Don't create features just because you can.**

### Rule 3

> **Avoid target leakage.**

### Rule 4

> **Respect the prediction-time information boundary.**

### Rule 5

> **Watch out for division by zero.**

### Rule 6

> **More features don't necessarily mean better performance.**

### Rule 7

> **Validate whether the feature actually improves the model.**
